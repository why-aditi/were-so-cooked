# Spike 5 — `step.waitForEvent` on the free plan

**Question (spec section 14):** Does `step.waitForEvent` work for the photo confirm flow on the free plan?

**Decides:** PhotoScan design.

**Run at:** 2026-09-25T05:30:33.683Z

## Answer

**Yes.** A Workflow on this account parked at `step.waitForEvent` with a 24-hour timeout and ran to completion 3115 ms after `sendEvent` was called. Note that it reports `running`, not `waiting`, the whole time it is parked — there is no waiting status to poll for, so the UI must track "awaiting confirm" itself. `PhotoScanWorkflow` can be built exactly as section 6 describes: extract, pause for the user's confirm list, commit, clean up. No polling loop or separate "pending scans" table is needed.

## What this changes

- **PhotoScan design:** keep `step.waitForEvent("confirm")` with the 24-hour timeout.
- **Step budget:** this flow costs 5 steps. At 3,000 steps a day that is 600 scans,
  far above anything a reviewer will do. Section 12's Workflows row holds.
- **R2 cleanup:** the clean-up step runs on the resume path. Timeout and failure paths still need their own cleanup, which this run did not exercise.

## Not covered

The 24-hour **timeout** path. Exercising it means waiting a day, so it gets a
separate long-running test rather than a spike. The 1-day R2 lifecycle rule in
section 4 is the backstop either way.
